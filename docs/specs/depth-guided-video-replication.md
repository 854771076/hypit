# 深度引导的视频复刻开发规格

状态：深度参考 MVP 已确认并开始实施；原生深度控制保留为后续增强
范围：Hypit Model、RunningHub Provider、作者工作流、Runtime 执行与验收
目标链路：文字脚本 + 人物参考图 + 原视频深度视频 + 分镜提示词 → 分镜视频 → 剪辑合成

## Problem Statement

当前视频复刻主要依赖文字脚本、人物参考图和分镜提示词。它可以复现人物外观和内容意图，但对原片的空间布局、人物与镜头距离、遮挡关系、景深变化和部分运镜轨迹缺少明确约束，因此生成结果容易出现构图漂移、前后关系错误和镜头运动不一致。

现有 RunningHub 集成已经可以通过工作流 `2098674379113979905` 把普通视频转换为灰度深度视频，但这只是预处理能力。MiniMax H3 和 Seedance 当前没有独立的深度控制端口；如果把深度视频作为普通参考视频提交，Provider 无法保证上游模型按深度控制解释它，也可能造成灰度风格污染。

真正的问题不是“生成一段深度视频”，而是建立一条类型明确、可计划、可复用、可失败恢复的两阶段依赖链：先从原镜头生成深度视频，再由 H3 或 Seedance 将该结果作为普通结构参考消费。

## Solution

为 Hypit 增加一条显式的深度参考视频复刻路径：

1. 原视频按已经确认的分镜边界形成镜头素材。
2. 每个镜头通过现有视频转深度能力生成深度视频 Artifact。
3. MVP 复用 MiniMax H3 和 Seedance 已有的 `ReferenceVideo`：人物图保持独立图片参考，深度结果作为普通视频参考，脚本与分镜方向合并为明确标注素材职责的 Prompt。
4. 文档和结果必须称为“深度参考生成”，不得宣称 H3 或 Seedance 获得了原生 Depth/ControlNet 能力；后续若接入真实深度控制协议，再增加独立精确 Model。
5. Runtime 根据图依赖先完成深度视频，再提交受控视频生成；各镜头可以在 Endpoint 容量范围内并行。
6. 生成的镜头视频继续沿用现有 Normalize、Timeline、Caption、Sound、Film 和 Rendering 流程完成剪辑合成。
7. 深度结果和成功镜头都作为普通 Result Output 保留，后续修改提示词、人物图或剪辑时可以显式复用，避免重复付费。

最终用户看到的是一条普通的 Hypit 作者链路，而不是 RunningHub 节点参数：作者声明创作意图和素材角色，Model 定义准确语义，Provider 负责映射实际工作流。

## User Stories

1. 作为视频复刻作者，我希望为每个原始镜头生成深度视频，从而保留原片的空间关系。
2. 作为视频复刻作者，我希望人物参考图与深度参考视频是两个不同输入，从而分别表达身份外观和空间运动意图。
3. 作为视频复刻作者，我希望脚本文字和分镜提示词保持独立，从而分别表达对白内容与镜头表现。
4. 作为视频复刻作者，我希望一个镜头的深度输出可以直接连接到受控视频生成，而不需要手工导出再导入。
5. 作为视频复刻作者，我希望可以只生成单个镜头进行验证，从而在整片生成前检查人物一致性和深度跟随效果。
6. 作为视频复刻作者，我希望深度生成成功而视频生成失败时可以复用已有深度结果，从而避免重复计算和付费。
7. 作为视频复刻作者，我希望修改字幕、配乐或剪辑时复用已生成镜头，从而不重新调用视频模型。
8. 作为视频复刻作者，我希望修改人物参考图时只重跑受影响的镜头，从而控制迭代成本。
9. 作为视频复刻作者，我希望系统明确告诉我所选 Provider 是否真正支持深度控制，从而避免得到看似成功但没有受控的结果。
10. 作为视频复刻作者，我希望计划阶段显示每个镜头的深度任务和参考生成任务，从而理解调用次数和依赖关系。
11. 作为视频复刻作者，我希望在提交前看到相关 Provider 的价格信息和不确定项，从而决定是否执行付费生成。
12. 作为视频复刻作者，我希望不同镜头可以在服务并发限制内并行执行，从而缩短整片等待时间。
13. 作为视频复刻作者，我希望超过上传上限或媒体类型错误在提交前被拒绝，从而避免无效远程任务。
14. 作为视频复刻作者，我希望深度处理或参考生成失败时保留任务 ID、工作流和公开错误信息，从而能够诊断问题。
15. 作为视频复刻作者，我希望已提交 Build 即使终端断开仍继续执行，从而不因观察连接中断而丢失任务。
16. 作为视频复刻作者，我希望最后的镜头视频仍是普通视频 Artifact，从而可以继续使用现有的时间线和渲染组件。
17. 作为 Provider 开发者，我希望深度角色在 Model 契约中明确表达，从而不会被错误映射成普通参考视频。
18. 作为 Provider 开发者，我希望一个 Provider 只声明自己真实实现的输入组合，从而保持跨厂商路由可信。
19. 作为运行维护者，我希望看到各阶段耗时、上传字节数、远程任务状态和失败原因，从而定位容量与服务问题。
20. 作为测试维护者，我希望不调用真实付费服务也能验证请求映射、异步轮询和结果收集，从而稳定运行 CI。
21. 作为项目协作者，我希望复刻流程和能力边界有清晰文档，从而知道哪些结果是深度受控、哪些只是普通参考生成。
22. 作为最终审核者，我希望能并排比较原镜头、深度视频和生成镜头，从而判断空间、动作、身份和画面质量是否达标。

## Implementation Decisions

### 1. 能力边界

- 保留现有“视频转深度”作为独立预处理 Model。它只负责从一个普通视频产生一个深度视频，不承担视频生成。
- MVP 不新增生成 Model：复用 H3/Seedance 的人物图片和普通视频参考端口，保持现有公共语义。
- 作者必须显式把人物图和深度视频声明为两个引用；Prompt 明确人物图负责身份外观，深度视频只负责空间、动作和运镜参考。
- Seedance 经 StarRouter 提交视频参考时必须携带实测 `duration-seconds`，并使用 `@图片N`、`@视频N` 标签；缺失或总时长不在 2–15 秒内时本地拒绝。
- 原生深度控制仍需要新的精确 Model、独立 `depthVideo` 端口和真实 Provider 协议，不在本 MVP 中伪装实现。

### 2. 原生深度控制的后续验收门槛

未来把能力升级为原生深度控制前，必须获得一个真实的深度受控视频生成工作流或 API，并确认：

- 工作流 ID 或模型 ID；
- 人物图输入节点和字段；
- 深度视频输入节点和字段；
- 提示词、脚本、时长、分辨率、画幅等可控字段；
- 输入视频编码、尺寸、帧率、时长和文件大小限制；
- 输出节点、输出媒体格式和任务状态协议；
- 深度含义，包括近远颜色方向、归一化方式、是否要求固定分辨率或帧率；
- 深度视频与输出镜头的时长、帧数和画面尺寸继承规则；
- 工作流是否真实使用深度控制，而不是仅把深度视频作为视觉参考。

如果缺少上述合同，开发只能完成深度预处理和作者编排草案，不能把功能标记为“深度受控复刻可用”。

### 3. 作者与执行数据流

关键异步路径如下：

```text
原镜头 Blob
  → 视频转深度 Need
  → RunningHub 深度任务
  → 深度视频 Blob
  → H3/Seedance 参考生成 Need
     ├─ 文字脚本/对白方向
     ├─ 人物参考图
     ├─ 深度视频
     └─ 分镜提示词
  → 将深度视频作为结构参考的 Provider 任务
  → 分镜视频 Blob
  → Normalize / Timeline / Film / Render
  → 最终成片
```

- 每个镜头是独立依赖分支；单镜头内部“深度生成→参考生成”严格串行，不同镜头之间允许并行。
- MVP 使用作者或参考分析阶段已经确认的分镜边界，不新增自动镜头检测系统。
- 原视频切片复用现有媒体处理能力；深度生成不负责切片。
- 深度视频和最终镜头都进入项目 Resource Store，并作为 Build Result 的公共 Output 保存。
- Run 通过现有 Candidate、`build-record` 和 `satisfy` 机制显式复用深度或镜头结果，不引入隐式缓存。
- 最终分镜视频继续暴露为普通视频 Blob，不为后续剪辑创建新的媒体类型。

### 4. Provider 和 Runtime

- RunningHub 继续使用固定深度工作流和现有 H3 路由；StarRouter 继续使用现有 Seedance 路由，仅补齐安全提交视频参考所需的时长验证。
- Provider 负责上传人物图和深度视频、填充节点字段、提交任务、保存 receipt、轮询状态、下载结果并写入 Resource Store。
- `supports` 在本地校验媒体数量、媒体类型、单文件 200MB 上限以及已知的时长、分辨率和帧率限制。
- 继续使用 Runtime 现有的异步 `start → poll → collect` 生命周期，不新增队列或微服务。
- 已确认远程 `taskId` 后立即 checkpoint。观察终端中断不影响 Build；恢复观察使用现有状态命令。
- 对没有 receipt 的超时不得自动重试付费提交，因为远程任务是否创建未知。由用户或 Agent基于 Result 证据创建新 Build。
- 一个 Build 不自动复用前一 Build 的深度和镜头结果；复用继续由 Run 明确选择。
- Provider 的凭据只通过 Runtime Profile 的 Credential Store 引用，不进入 Source、Run、日志或 Result。

### 5. 兼容性与演进

- 现有 MiniMax H3、Seedance、RunningHub 深度转换以及其他 Provider 路由保持兼容。
- MVP 不新增 capability reference，因此旧 Profile 不需要迁移；只需确保深度预处理与所选 H3/Seedance Endpoint 已绑定。
- 新 Provider 路由只在安装对应 Model 后参与解析。
- Profile 可以单独绑定深度预处理与 H3/Seedance 参考生成到不同 Endpoint；不要求两个阶段使用同一家服务。
- 后续若另一个真实模型支持相同作者语义，应优先判断它是否确实实现同一精确 Model；协议或语义不同则新增独立 Model，而不是只替换 `baseUrl`。

### 6. 容量与资源假设

- 当前 RunningHub Endpoint 默认并发为 2，MVP 继承该容量，不新增全局调度器。
- 对含 `N` 个镜头的复刻，最多产生 `N` 个深度任务和 `N` 个参考生成任务；复用可以减少其中任意一类。
- 单镜头生成链的远程任务数为 2，关键路径延迟约为两次任务耗时之和；不同镜头由 Runtime 在 Endpoint 容量内流水执行。
- 单镜头上传至少包括原镜头一次、人物图一次和深度视频一次。实际带宽由镜头长度、编码和是否复用决定，不在缺少样本时伪造精确估算。
- 保留现有 200MB 单项上传硬上限。真实生成工作流若更严格，以其限制为准。
- 现有请求超时、操作超时和轮询间隔继续作为配置项；只有实测表明不足时才调整默认值。
- 在首个真实样本验证中记录：输入时长、分辨率、文件大小、深度耗时、生成耗时、上传量和输出大小，用于替换以上假设。

### 7. 故障模型与恢复

| 故障 | 用户可见行为 | 恢复方式 |
| --- | --- | --- |
| 原视频无法读取或超限 | 计划或提交前拒绝 | 修正素材后重新计划 |
| 深度工作流失败 | 当前镜头不进入参考生成 | 保留其他镜头结果，修复后新建 Build |
| 深度成功、参考生成失败 | 深度 Output 保留 | 新 Run 显式复用深度后重试生成 |
| Provider 变慢或排队 | Build 显示 pending 和阶段 | 继续观察，不重复提交 |
| 提交超时且无 receipt | Build 失败并标记远程结果未知 | 核对服务侧任务后再决定是否新建 Build |
| 轮询返回未知状态 | 保留 taskId 和公开响应证据 | 修复状态映射后用新 Build 或人工取回产物 |
| 下载结果失败 | 保留远程 receipt 和 URL 证据 | 在授权范围内重新收集，避免重新生成 |
| 凭据或额度失败 | 明确报告 Endpoint 和公开原因 | 更新同一账户配置或由用户选择新路线 |
| 单镜头失败 | 其他镜头继续完成 | 只重跑失败镜头并复用成功 Outputs |
| Runtime 进程终止 | 当前尝试结束，Result 保留完成项和 receipts | 新 Build 显式复用已有结果 |

### 8. 安全与可观测性

- API Key 仅存在于 Credential Store；日志不得输出请求头、Key、带签名下载 URL 或完整私有素材地址。
- 原视频、人物图和深度视频都按用户媒体处理；Resource Store 和 Result Repository 沿用项目边界及其访问控制。
- Provider 日志记录 capability、Endpoint、工作流 ID、远程 taskId、阶段、耗时、上传字节数和公开错误码。
- 监控重点包括任务提交失败率、排队/运行时长、轮询错误率、下载失败率、每镜头上传量和 Endpoint 容量等待时间。
- 首版不引入分布式追踪平台；使用现有 Build 日志、receipt、activity 和 status 即可覆盖故障定位。
- 发布前准备一个可回滚的 Provider 版本；回滚只移除新路由，不修改或删除已有 Result。

### 9. 制作合同与质量门禁

- `SHOTS.md` 先记录语义事件，再记录编译后的秒数和帧号。对白词语、动作完成态和剧情交接
  是时间的所有者；换选音画结果、修改对白或改变上游保留时长后，必须重编译所有依赖事件。
- 一帧门禁分别保存目标编译帧、选定成片中的实测帧和二者差值；不得用生成结果反向改写目标
  来制造通过。目标未批准或实测未完成时状态必须保持 blocked。
- 每个 1–3 秒原子镜头分别记录人物/场景/道具版本、分镜类型、首尾连续性、Provider、模型、
  原生音频、验收项和有序参考清单。
- 每镜深度状态为 `generate | reuse | waived`。默认 RunningHub 工作流
  `2098674379113979905`，并记录源镜头、预期本地 Output、选定 Result 与审核状态；豁免必须有
  具体原因。
- 最终选定的生成音画 Result 是对白时间依据。换选或重生对白镜头后，旧逐词时间、字幕和
  口型修复全部失效，依赖事件回到 blocked；原片音轨只用于分析，不进入完整重制的时间线。
- 精确倒计时等剧情文字按读数分别生成静态或近静态视觉资产。每个状态通过原分辨率人工检查
  和 OCR 后成为不可变资产，由 Hypit Timeline 在语义事件编译帧切换；视频模型不得重绘字符
  或决定转换时间。
- 普通镜头默认两个候选，明确的高风险镜头可批准第三个。同一可见原因连续失败两次后停止
  等价付费重试，返回分镜、参考绑定、连续性或模型选择，并重新确认新增预算。
- 当 Brief 要求完整重制时，最终时间线引用原片画面和原片音频的数量必须均为零。

这些合同保存在项目笔记和显式 Source/Run 图边中，不新增 Runtime 状态机。Prompt Kit 负责
生成可审阅文本，文件存在、OCR、人物一致性和一帧容差仍由计划及媒体审核门禁验证。

### 10. 分阶段实施计划

#### 阶段 0：MVP 路径确认（已完成）

- 确认工作流 `2098674379113979905` 只负责视频转深度。
- 确认 H3 与 Seedance MVP 通过现有普通视频参考端口消费深度结果。
- 明确这是软参考而非原生 Depth/ControlNet；真实强控制工作流作为后续增强。
- 退出条件：Model 和 Provider 的现有接口能够表达人物图与深度视频两条独立图边。

#### 阶段 1：复用现有 Model 契约

- 保持 H3/Seedance capability 不变，通过 `ReferenceVideo` 独立表达人物图和深度视频。
- 为 Seedance 视频参考增加可选的 `duration-seconds` 元数据。
- 补充 package README、Skill、作者示例和请求验证。
- 退出条件：合法请求可生成 Need，StarRouter 所需时长或标签缺失时在本地被拒绝。

#### 阶段 2：Provider 路由

- 保持 RunningHub H3 与视频转深度路由不变，直接复用 H3 的视频参考上传。
- 允许 StarRouter Seedance 提交带实测时长的视频参考，并生成对应 `@视频N` 多模态内容。
- 不再把 `personReference` 等同于“真人脸”；人物参考属性与服务侧真人限制是不同语义。
- 退出条件：契约测试证明人物图和深度视频进入各自多模态条目，缺少视频时长时拒绝提交。

#### 阶段 3：作者编排与复用

- 提供“原镜头→深度→H3/Seedance 参考生成”的 Source 示例。
- 提供单镜头 material Run 和整片 production Run 示例。
- 演示深度成功后复用、单镜头重跑和最终成片复用。
- 退出条件：`check` 和 `plan` 显示两阶段依赖及正确 Endpoint，重复剪辑不会重新生成素材。

#### 阶段 4：真实样本与质量验收

- 使用一个短镜头完成真实 Build。
- 对比原 RGB、深度结果、无深度基线和深度参考结果。
- 检查人物身份、姿态、遮挡、近远关系、镜头运动、闪烁、边缘和音画时长。
- 记录成本、延迟、失败恢复和已知限制。
- 退出条件：深度版本在预先定义的空间一致性指标上优于无深度基线，且没有不可接受的身份或画质退化。

#### 阶段 5：文档与发布

- 更新 Provider、Model、Skill 和中英文服务说明。
- 说明支持矩阵、输入限制、费用、不支持时的明确行为和复用方式。
- 完成定向测试、全仓类型检查、发行包检查和安装验证。
- 退出条件：本地安装可发现 Model/Provider，示例可计划，旧能力回归通过。

## Testing Decisions

- 测试只验证公开行为和跨模块合同，不断言内部辅助函数或节点构造过程之外的实现细节。
- 首选最高层测试缝：深度转换继续覆盖 RunningHub `start → poll → collect`；参考生成覆盖 H3/Seedance Request 到 Provider 多模态请求映射。
- Model 合同测试覆盖：一个人物图、一个深度视频、必需文本字段、缺失输入、重复输入、错误媒体角色和边界值。
- Provider 路由测试覆盖：正确深度 workflow ID、H3 图片/视频参考、Seedance 图片/视频条目、视频时长、Prompt 标签、200MB 限制以及不支持组合。
- 异步生命周期测试覆盖：提交成功 checkpoint、排队、运行、成功但结果尚未出现、业务失败、超时、未知状态、下载失败和最终收集。
- 图级计划测试覆盖：一个作者示例应产生先深度后参考生成的两个 Need；显式选择深度 Result 后只剩参考生成 Need；选择最终镜头后两者都不再提交。
- 兼容性测试覆盖现有 MiniMax H3、Seedance 和视频转深度路由，确保新增视频时长元数据没有改变既有请求和 workflow ID。
- 真实服务验证不进入默认 CI，避免密钥和付费调用；使用人工授权的短镜头 smoke test，并保存脱敏后的请求事实和 Result 元数据。
- 质量验收使用同一镜头的无深度基线进行对照，至少检查：主要人物轮廓位置、前后遮挡顺序、相对尺度、镜头移动方向、帧间稳定性和身份一致性；该对比只评估软参考效果，不得称为原生深度控制。
- 第一条实现测试应沿用现有 Provider 测试风格和 Memory Resource Store，不新增测试框架。
- Prompt Kit 测试覆盖精确剧情文字单状态、Seedance 必填语义时序，以及 H3 六段式顺序保持不变。
- CLI `check` 只验证公开 Source 能被解析；`plan` 验证完整示例仍形成深度→H3 两阶段依赖，且
  Script 或语义时序变更会改变生成请求。制作门禁不得错误宣称由 `check` 自动执行。
- 审片必须验证编译切点和对白首尾不超过一帧、OCR 只包含批准文字、最终时间线不存在原片
  画面或音轨，并验证换选音画结果后没有沿用失效的字幕或口型资产。

## Out of Scope

- 自动镜头检测、自动分镜理解或自动改写脚本。
- 新建调度微服务、消息队列、数据库或隐式内容缓存。
- 声称 H3/Seedance 的普通深度参考视频等同于原生 Depth/ControlNet 控制。
- 在没有真实协议证据时声称任意 Provider 支持深度控制。
- 训练、微调或部署新的深度估计/视频生成基础模型。
- 自动判断深度控制强度、自动选择最佳生成结果或自动修复失败镜头。
- 改造现有 Timeline、Film、Caption、Sound 或最终编码架构。
- 跨 Build 自动重试可能产生费用的远程提交。
- 第一阶段同时支持多人物、多深度层或多路深度输入。

## Further Notes

### 上下文和信任边界

- 作者边界：SVML/SVRun 只描述素材角色、创作参数、目标和复用选择。
- Runtime 边界：负责解析依赖、选择 Endpoint、容量调度、持久化 receipt 和 Build 状态。
- Provider 边界：负责 RunningHub 协议、节点映射、远程错误和结果下载。
- 外部信任边界：RunningHub 接收私有媒体和 API Key，并返回任务及媒体 URL；必须按第三方服务处理数据和可用性风险。
- 项目存储边界：Resource Store 保存工作媒体，Result Repository 保存公共 Outputs 和执行证据。

### 关键风险

1. 最大风险是 MVP 只有普通视频参考语义，空间跟随强度和稳定性弱于真正的深度受控生成工作流。
2. 深度视频可能与生成模型要求的近远方向、归一化、分辨率或帧率不一致。
3. 单张人物图不足以覆盖大角度转身、遮挡和复杂动作，可能需要多视图人物资产，但不应在 MVP 中预设。
4. 深度约束增强空间一致性时可能降低身份、纹理或光照质量，需要基线对照确定可接受权衡。
5. 两次远程任务会增加每镜头延迟、上传量和成本；显式复用是首版最重要的成本控制手段。
6. RunningHub 工作流节点升级可能破坏固定映射，应通过模板完整性检查和 provider contract test 尽早发现。

### ADR-001：MVP 复用普通视频参考，原生控制另立能力

- 决策：已确认的 MVP 显式把深度视频作为 H3/Seedance 的普通 `referenceVideo`，并在 Prompt 和文档中标记其结构参考职责。
- 原因：现有 Model 与 Provider 已覆盖这条图依赖，可先验证真实效果，无需虚构尚不存在的强控制协议。
- 代价：不能保证模型按几何控制解释深度，结果可能出现灰度污染或结构漂移。
- 升级条件：获得可验证的原生深度工作流/API 后，新增独立 `depthVideo` 端口和 capability，不改变本 MVP 的历史语义。

### ADR-002：继续使用现有 Build 图和异步 Provider 生命周期

- 决策：两阶段任务通过普通 Need 依赖连接，继续使用 Runtime 的容量、checkpoint、Result 和显式复用机制。
- 原因：现有架构已经覆盖异步任务、断线观察、失败证据和跨 Build 复用，没有新建编排服务的真实需求。
- 代价：每次重试必须创建新 Build，并在 Run 中明确选择可复用 Output。
- 替代方案：Provider 内部同时执行深度和生成；因隐藏中间结果、削弱复用与故障恢复而拒绝。

### ADR-003：先支持预先确认的分镜边界

- 决策：MVP 不实现自动镜头检测，使用参考分析或作者给出的镜头范围。
- 原因：本功能的核心风险是深度控制协议和质量，不应同时引入另一个识别系统。
- 升级条件：真实项目反复证明手工/分析分镜成为主要耗时或一致性瓶颈后，再单独设计自动检测能力。
